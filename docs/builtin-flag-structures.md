# Builtin flag data structures (design options)

Goal: one data structure that stores the flags of a fish command, and which flags
can't be combined. It is used to show a diagnostic when flags that can't be used
together are combined. It has to be fillable from two sources:

1. **Hardcoded builtins**, generated by `scripts/gen-builtin.ts` from fish itself
2. **User-defined functions**, parsed from their `argparse` call (`-x`/`--exclusive` defines mutually exclusive flags)

Example used throughout, `fish_add_path`'s `argparse` (`status get-file functions/fish_add_path.fish`):

```fish
argparse -x g,U -x P,U -x a,p g/global U/universal P/path p/prepend a/append h/help m/move v/verbose n/dry-run -- $argv
```

## Current state & known problems

### Defining conflicts (`Option.conflictsWith()` / `Option.mutuallyExclusive()`)

- Conflicts are stored as references to other `Option` objects, in both directions.
- Two separately built `Option.create('-g','--global')` objects don't conflict with each other.
- Two Options that both claim the same flag (e.g. `-r`): `options.find()` takes the first one, and
  conflicts on the second are silently ignored. Nothing warns about it.
- "Pick one of N" groups (the `set` scope flags `-l -g -U -f`) are flattened into N(N-1)/2 pairs,
  so a diagnostic can't say "only one of `-l -g -U -f`".

### Checking a script (`findFlagIssues`)

- It walks the flags in order and reports the later flag of a pair, pointing back at the earlier one.
- A repeated flag (`-g -g`) is not a conflict.
- **False positive:** shortened long options are reported as unknown (see below).

### Long-option abbreviation (the `short_s` bug)

fish accepts shortened long options (documented under `argparse --strict-longopts`; builtins parse the same way):

- `--sh` works as `--show` if no other long flag starts with `sh`
- `-show` / `-sho` / `-s` work as `--show` if `-s` isn't a short flag of its own

So `set -s`, `fish_add_path -d` (`--dry-run`) and `-u` (`--universal`) are accepted by fish,
but they aren't real short flags. `argparse -S` turns this behaviour off.

### Generator gaps

- Brute-forced short flags that are really abbreviations came out as `short_x` (fixed: see `probeFlag`).
- The combination check doesn't match fish's `cannot both export and unexport` /
  `cannot both path and unpath` messages, so `set -x -u` and `set --path --unpath` are missed.

## Option A: conflicts stored on `Option` objects (what exists now)

```ts
const global = Option.create('-g', '--global');
const universal = Option.create('-U', '--universal');
global.conflictsWith(universal);
```

- **Pro:** it already exists.
- **Con:** relies on object references, can't be saved as JSON, expands groups into pairs, no record of where a rule came from.
- **Con for argparse:** the parsed `argparse` call has to be turned into objects and pairs, which loses the `-x g,U` source text.

## Option B: plain data shaped like argparse, with exclusive groups (recommended)

```ts
type ArgKind = 'none' | 'required' | 'optional' | 'multiple' | 'optional-multiple' | 'integer'; // '' '=' '=?' '=+' '=*' '#'

interface FlagSpec {
  id: string;                 // argparse variable name: long if present, else short → `_flag_${id}`
  short?: string;             // 'g'
  long?: string;              // 'global'
  arg: ArgKind;
  hiddenShort?: boolean;      // argparse `n-name` form: short isn't usable by the user
  description?: string;
  range?: LSP.Range;          // argparse source location of this option spec
}

interface ExclusiveGroup {
  flags: string[];            // FlagSpec ids, at most one of them may be used
  range?: LSP.Range;          // the `-x g,U` token, shown as related info in the diagnostic
}

interface CommandSpec {
  name: string;
  source:
    | { kind: 'builtin'; fishVersion: string; }
    | { kind: 'argparse'; uri: string; range: LSP.Range; };
  flags: FlagSpec[];
  exclusive: ExclusiveGroup[];
  subcommands?: CommandSpec[];
  args?: { min?: number; max?: number; };         // argparse -N / -X
  parsing?: {
    stopAtFirstArgument?: boolean;                // argparse -s, set's `+LSUaefghlnpqux`
    longAbbreviations?: boolean;                  // false with argparse -S
    allowUnknown?: boolean;                       // argparse -u / -i
  };
}
```

Hardcoded builtin:

```ts
export const fishAddPath: CommandSpec = {
  name: 'fish_add_path',
  source: { kind: 'builtin', fishVersion: '4.9.3' },
  flags: [
    { id: 'global', short: 'g', long: 'global', arg: 'none' },
    { id: 'universal', short: 'U', long: 'universal', arg: 'none' },
    { id: 'path', short: 'P', long: 'path', arg: 'none' },
    { id: 'prepend', short: 'p', long: 'prepend', arg: 'none' },
    { id: 'append', short: 'a', long: 'append', arg: 'none' },
    // help, move, verbose, dry-run ...
  ],
  exclusive: [
    { flags: ['global', 'universal'] },
    { flags: ['path', 'universal'] },
    { flags: ['append', 'prepend'] },
  ],
  parsing: { longAbbreviations: true },
};
```

Parsing a user's `functions/fish_add_path.fish` gives exactly the same shape, with
`source: { kind: 'argparse', ... }` and a `range` on each flag and group:

| argparse | CommandSpec field |
|---|---|
| `g/global` | `FlagSpec` |
| `-x g,U` | `ExclusiveGroup` (short or long names resolved to ids) |
| `-N` / `-X` | `args` |
| `-s`, `-S`, `-u` | `parsing` |

- **Pro:** one format for both sources; saves as JSON (generator can write `.ts` or `.json`);
  keeps "at most one of these", which gives better diagnostic messages; can point back at the `-x` that caused the rule.
- **Con:** checking needs a lookup table built from the data (Option E).

## Option C: B, with a general rule list instead of only exclusive groups

```ts
type FlagRule =
  | { kind: 'exclusive'; flags: string[]; range?: LSP.Range; }
  | { kind: 'requires'; flag: string; requires: string[]; }      // a flag only valid alongside another
  | { kind: 'oneOfRequired'; flags: string[]; };                  // at least one must be present
interface CommandSpec { /* ...as B, but */ rules: FlagRule[]; }
```

- **Pro:** room for builtin rules that `argparse` can't express.
- **Con:** more than either source produces today; `argparse` only ever produces `exclusive`.

Build B, and keep its field easy to widen into C later.

## Option D: conflict table (what the generator actually measures)

```ts
interface ConflictMatrix { flags: string[]; conflicts: Array<[string, string]>; } // pairs fish rejected
```

The generator's raw result, not something to store. Each check only proves two flags can't be
used together, so the step to B is: **group pairs that all conflict with each other**. Find the
largest sets of flags where every pair conflicts, and make each set one `ExclusiveGroup`.

`set` example: `-f -g -l -U` all reject each other, and each also rejects `-S`, so they form one
group `{show, function, global, local, universal}`. Nothing is lost, because every pair inside a
group really was rejected. It's the same expressive power as argparse `-x`, so builtins and user
functions end up identical.

## Option E: lookup table built at runtime (derived from B, never stored)

```ts
class CommandIndex {
  constructor(readonly spec: CommandSpec) {}
  private byShort: Map<string, FlagSpec>;      // 'g' → global
  private byLong: Map<string, FlagSpec>;       // 'global' → global
  private groupsOf: Map<string, ExclusiveGroup[]>;
  resolve(token: string): FlagSpec[] | 'unknown' { /* see below */ }
  validate(args: SyntaxNode[]): FlagIssue[] { /* see below */ }
}
```

`resolve` follows fish's parsing order:

1. `--x` is an exact or uniquely shortened long flag.
2. For `-xyz`: if `x` is a known short flag, read it as the cluster `-x -y -z`, where a flag taking a value swallows the rest of the token.
3. Otherwise, if abbreviations are allowed, read `-xyz` as `--xyz`.

`validate` tracks which flags were used. For each group, any flag after the first one used gets a
diagnostic, with related info pointing at the first one and at the group's `-x` token.
This replaces the current `Option` / `findFlagIssues` pairing; `Option` could become a thin wrapper around `FlagSpec`.

## Recommendation

B as the one format both sources produce, E as the checker built from it:

```
gen-builtin.ts ──(pairs → groups, D)──┐
                                      ├──► CommandSpec (B) ──► CommandIndex (E) ──► diagnostics
argparse in a user's function ────────┘
```

Parsing `argparse` from a user's function:

- **Which calls count:** only `argparse` calls in a function body where the spec words are literal
  text after the `argparse` options and before `--`.
- **Skip dynamic specs:** `argparse $opts -- $argv` → skip or mark partial, never produce false diagnostics.
- **Several calls in one function:** usually a function handling its own subcommands with `-s`; handle the first call only to start.

Generator changes for B:

- Group the conflicting pairs into exclusive groups instead of emitting `conflictsWith()` lines.
- Drop single-character flags that are really long-option abbreviations (done).
- Match `cannot both` in the conflict check.
- Record the `+` stop-at-first-argument behaviour where the fish source shows it.
